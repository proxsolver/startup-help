# 모두의 창업 정산 도우미 (비공식)

지원사업(모두의 창업) **참여자**가 사업비를 집행하고 지출증빙을 모아 정산·보고하도록 돕는
정적 안내 사이트 + 브라우저 전용 집행 정리 도구.

> 이 사이트는 중소벤처기업부·창업진흥원의 공식 안내가 아닙니다. 공식 안내는 [modoo.or.kr](https://modoo.or.kr) 입니다.

- 배포: GitHub Pages (정적 파일, 서버 없음)
- 사용자 데이터: `window.localStorage` 에만 저장. 어떤 입력도 네트워크로 전송하지 않음
- 콘텐츠 원칙: **제출 시점·한도·인정 범위 같은 수치는 1차 출처 검증 전에는 게시하지 않는다**

## 구조

```
src/
  content/guides/{basics,expense,settlement,documents}/*.md   안내 문서 (frontmatter 스키마 검증)
  content.config.ts                                     Zod 스키마. sources 1개 이상 필수
  data/{checklists,schedule,categories}.ts              체크리스트·정산/제출 항목·분류 메타
  lib/{receipts,storage,url}.ts                         순수 로직 (단위 테스트 대상)
  components/                                           Header/Footer/Checklist/ReceiptTool/…
  layouts/Base.astro                                    공통 shell (라이트/다크, og, canonical)
  pages/                                                index, guide/, calendar/, tools/, 정보 페이지
  plugins/baseLinks.js                                  마크다운 루트 링크에 Pages base 경로 부착
scripts/check-content.mjs                               콘텐츠·게이트 (7개 규칙)
scripts/check-dist.mjs                                  빌드 결과(배포물) 검사: 끊긴 링크·(비공식) 표기·canonical
tests/*.test.ts                                         vitest
```

## 정리 도구가 갖는 항목 (스키마 v2)

한 건 = `{ 지출일, 거래처, 금액, 비목(예산과목), 결제경로, 집행기간, 증빙종류, 수취상태, 제출상태, 메모 }`

| 축 | 값 | 왜 따로 두나 |
| --- | --- | --- |
| 결제경로 | 전용(체크)카드 · 사업자·법인카드 · 개인카드 · 현금 · 계좌이체 · 간편결제 · 기타 · 확인 필요 | 어느 경로로 결제했는지가 받을 수 있는 서류를 정합니다 |
| 집행기간 | 기간 내 · 기간 외 · 확인 필요 | 기간 밖 지출이 정산에서 가장 많이 잘립니다 |
| 증빙종류 | 세금계산서 · 계산서 · 현금영수증 · 카드전표(매출전표) · 간이영수증 · 계약서·견적서만 · 없음 | 세무 일반 용어이며 정산 인정 여부와는 별개입니다 |
| 수취상태 | 원본 확보 · 사본·이미지만 · 미수취 · 재요청함 | 정산은 파일로 받습니다. 종류만 알고 파일이 없으면 미수취와 같습니다 |
| 제출상태 | 미제출 · 초안 포함 · 제출 완료 · 보완 요청 | 보완 요구를 목록으로 되돌려 받아야 합니다 |

비목은 협약서의 예산과목 이름을 그대로 쓰도록 **자유 입력(예시 목록 제공)** 으로 두었습니다.
집계 화면은 총 집행액 / 전용카드 비율 / 수취구멍 / 기간 리스크 / 제출 전 합계를 나오고,
CSV 는 11열 대조표(`execution_*.csv`, UTF-8 BOM + CRLF)로 나갑니다.

**v1 데이터 호환**: 구버전 저장값(`category`, 결제수단 `카드`, `신용카드매출전표` 등)은
읽는 시점에 `sanitizeEntries → normalizeEntry` 에서 v2 로 승격됩니다. 판별은 v1 전용 필드
(`category` · `regularEvidence` · 결제수단 `카드`) 기준으로 하므로, v2 항목이 재승격으로 손상되지 않습니다.

## 실행

```bash
npm install
npm run dev            # http://localhost:4321 (base: /startup-help/)
ASTRO_LOCAL=1 npm run dev   # base 없이 루트로 (로컬 확인용)
npm test               # 정리 도구·저장 로직 단위 테스트
npm run check:content  # 출처/수치/링크/섞임 문자/게이트 데이터 게이트
npx astro check        # 타입 검사 (.astro 포함)
npm run build          # dist/ 정적 출력
npm run check:dist     # 배포물 검사: 내부 링크 441건·모든 화면 (비공식) 표기
```

## 저장 규칙 (브라우저 전용, 그래서 더 엄격하게 지킨 것들)

`window.localStorage` 의 `startup-help/state/v1` 한 개 키에 담습니다. 서버는 없습니다.

| 상황 | 동작 |
| --- | --- |
| 두 탭이 열려 있을 때 | 쓰기 직전 저장된 값을 다시 읽어 **항목 단위로 합칩니다** (`mergeEntries`). 한 탭의 입력이 다른 탭 저장에 사라지지 않고, 다른 탭이 저장하면 `storage` 이벤트로 화면에 반영됩니다 |
| 삭제한 항목 | 지운 id 를 저장소의 `removed` 에 남깁니다. 오래 열어 둔 다른 탭이 같은 id 를 다시 보내도 되살아나지 않습니다. 최근 500개만 보관, JSON 복원 시 파일 값으로 대체 |
| 지출 저장 vs 체크리스트 저장 | 각각 자기 영역만 씁니다 (`saveEntries` / `saveChecklist`). 한 화면의 저장이 다른 화면의 데이터를 덮어쓰지 않습니다 |
| 저장된 데이터가 이 코드보다 새로운 스키마 | **쓰기를 거부**하고 읽기만 합니다. 형식 강등은 되돌릴 수 없어서입니다 |
| 읽지 못한 행 | 개수를 화면에 표시합니다(조용히 버리지 않음) |
| JSON 복원 | 목록은 **대체**, 체크리스트는 보존. 더 새로운 형식의 파일은 복원하지 않음 |
| 지출 목록 비우기 | 지출만 삭제. 체크리스트는 그대로 |
| 시크릿 창·용량 초과 | 저장이 실패함을 배너로 보여줍니다 |

## 배포

`.github/workflows/deploy.yml` 이 push 시 `check:content` → `astro check` → `test` → `build` → `check:dist` → Pages deploy 를 순서대로 실행합니다.
저장소 Settings → Pages → Source 를 **GitHub Actions** 로 두면 첫 deploy 가 붙습니다.

배포 경로가 `/startup-help/` 인 이유는 프로젝트 페이지이기 때문입니다. 커스텀 도메인을 쓰면
`astro.config.mjs` 의 `REPO`/`site`/`base` 를 고치세요. 콘텐츠 안의 링크는 `src/plugins/baseLinks.js` 가,
컴포넌트 안의 링크는 `src/lib/url.ts` 의 `p()` 가 자동으로 앞경로를 붙입니다.

## 검증 상태 모델 (핵심 설계)

문서·정산 항목마다 `verification: 'verified' | 'pending'` 을 가집니다.

| 상태 | 화면 동작 |
| --- | --- |
| `pending` | 문서 상단에 "출처 검증 대기" 배너. 시점·금액은 **빈칸** + 공식 창구 링크. 푸터에 대기 건수 표시 |
| `verified` | 배너 없음. 검증된 값과 출처가 본문·`sources` 에 존재 |

`pending` 문서가 `만원`/`억원`/`가산세`/`제N조`/보존기간·기한 수치를 쓰면 `npm run check:content` 가 빌드를 실패시킵니다.
같은 게이트가 한자·가나 섞임 문자도 전체 소스에서 잡아냅니다.
즉 "임의 수치를 올리지 않는다" 가 사람의 주의가 아니라 CI 규칙으로 강제됩니다.

게이트가 문서(md)만 보면 코드 쪽 데이터가 빠져나갑니다. 그래서 같은 규칙을 코드에도 적용합니다.

- **일정표도 같은 법칙** — `src/data/schedule.ts` 의 `pending` 항목은 `dueText` 를 채울 수 없고,
  설명에 검증 안 된 수치를 쓸 수 없으며, 확인 창구 링크(공공 기관 도메인 또는 이 사이트)와
  `decidedBy`(그 값이 협약서·공지·원문 중 어디서 확정되는지) 를 반드시 가져야 합니다.
- **링크는 두 번** — 문서 본문·컴포넌트·체크리스트에 적힌 `/guide/...` 경로가 실제 라우트인지 검사하고(주석 속 예시는 제외),
  빌드 뒤에는 `dist` 의 모든 `href`·`src` 를 실제 파일로 되역해 확인합니다(`check:dist`).
- **제목도 검사** — `check:dist` 는 모든 화면 `<title>` 에 `(비공식)` 이 있는지와 canonical 1개를 확인합니다.
  공유 미리보기·브라우저 탭이 공식 기관 페이지처럼 보이는 것을 막는 지점입니다.
- `verification` 을 아예 적지 않으면 기본값이 `pending` 이라 수치 금지·검증 메모 요구가 함께 걸립니다(게이트 우회 방지).

## 아직 안 채운 것 (그리고 막힌 이유)

시점·한도·인정 범위는 **두 축**으로 나뉘고, 채운 쪽과 막힌 쪽이 다릅니다.

**채운 축 (세법이 정하는 시점)** — 2026-10-24 에 국가법령정보센터 본문에서 확인해 반영했습니다.

- 부가가치세 확정신고: 과세기간 종료 후 25일 이내 (부가가치세법 제49조①) + 국세청 달력 안내
- 종합소득세 확정신고: 다음 연도 5월 1일~31일 (소득세법 제70조①)
- 원천세: 지급일이 속한 달의 다음 달 10일, 반기납부 특례 (국세청 원천세 신고납부기한 안내)
- 지출증빙 보관: 확정신고기간 종료일부터 5년 (소득세법 제160조의2①) / 상법 장부·중요서류 10년, 전표 5년 (상법 제33조①)
- 현금영수증 의무발급: 건당 거래금액(부가세 포함) 10만원 이상, 대상 업종은 대통령령 (소득세법 제162조의3④)

확인하지 않은 값(법인세법·부가가치세법상 보관 개수, 간이과세자 기준액)은 `/guide/settlement/tax-obligations/` 의 "확인하지 못해 비워 둔 것" 에 적어 두고 게시하지 않았습니다.

**막힌 축 (지원사업이 정하는 시점)** — 사업별 세부관리기준·협약서·담당 주관기관 정산 안내가 필요합니다.

- `modoo.or.kr` 은 봇 요청을 차단합니다(HTTP 429 + Vercel 챌린지). 사람이 브라우저로는 볼 수 있어도 자동 검증이 안 됩니다 → **출처 미확보** 상태이지, 사실이 아니라는 결론이 아닙니다.
- 법제처의 **행정규칙**(운영요령·통합관리지침, `admRulLsInfoP.do`) 페이지는 본문이 JS 렌더링이라 원문을 가져오지 못했습니다. **법령 본문**(`lsInfoP.do`) 은 브라우저 렌더링으로는 확인 가능해 위 수치에 반영했습니다.
- `k-startup.go.kr` 공고 상세는 POST 조회 화면이라 직걸기하면 빈 셸입니다.
- 그래서 지원사업 축은 값은 비우고 **확인 창구 + 값이 확정되는 자리** 를 먼저 보여주는 구조로 배포했습니다.

남은 작업:
- 참여자가 받은 **협약서·세부관리기준·정산 안내 PDF** 가 있으면 그 원문을 1차 출처로 채워 `dueText` 와 문서를 반영합니다(가장 빠른 길입니다).
- **문서 서식(샘플 양식)**: 집행내역서·증빙 대응표·정산 요약 서식은 서식 기준 검증 후 추가
- 개인정보 처리방침의 법적 의무 범위 확인 (현재는 운영 사실 서술만)
- OCR·사진 인식 (서버 수신 없이 구현 가능한지 먼저 검토)
- 접근성·E2E 자동 테스트 (현재: 단위 테스트 64 + 콘텐츠 게이트 + 빌드 검사)
- 콘텐츠 증량 (현재 8건)
